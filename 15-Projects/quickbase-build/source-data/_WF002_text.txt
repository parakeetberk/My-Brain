Version History Section 01 Document Purpose WF002 — Rehab This specification defines the complete Quickbase (QB) tables, workflow stages, automations, gate rules, and FastField form required to build Workflow #002: Rehab . WF002 manages the end-to-end process of taking an existing home from a Rehab disposition decision — made via the TBD Report or manually — through completed rehabilitation, final walkthrough approval, and handoff notification to the listing team. WF002 is independent of WF001 (Home Ordering). WF001 covers new homes ordered from manufacturers. WF002 covers existing homes in the portfolio that require rehabilitation before they can be re-listed or re-occupied. System of Record: Rent Manager (RM) remains the authoritative source for asset data, financial records, insurance, and lease history. This build complements RM — it does not replace or auto-modify any RM records. All RM field references in QB are cross-references only. No data is written back to Rent Manager from QB. Boundary Detail In Scope All 9 rehab workflow stages; QB tables (Lot Status ref, Asset Status ref, Rehab Records, Rehab Tasks, Walkthrough Records, Vendors); FastField Rehab Walkthrough Punchlist form with photo capture; FastField → QB webhook integration; all automations and gate rules defined in this document; 68-community Communities table (from dw_PDS.xlsx) Out of Scope Rent Manager record creation or modification; marketing execution after listing; Workflow #001 (new home ordering); invoice processing or payment; vendor portal access; WF003 Asset Disposition Review meeting design (separate workflow — see Q-037) Dependent Workflows WF003 Asset Disposition Review (proposed) — weekly Monday meeting assigns Rehab / Demo / Turn for Sale dispositions; triggers WF002 when disposition = Rehab. Move Out workflow — completed move-out can trigger WF002. Listing workflow — WF002 notifies listing team at Stage 8; listing team initiates listing manually. Cascading Dropdowns WF002 uses cascading dropdown logic in QuickBase to reduce data entry errors and narrow selection lists to contextually valid choices. The primary cascade chain is Community → Lot Number → (pre-populated unit data) . A secondary chain filters the Vendor ID dropdown by trade category and by the community's state. 8.1 Primary Cascade: Community → Lot Field Source Cascade Logic Community QB Communities table Unrestricted dropdown of all Active communities (Short Name + Display Name). Drives the Lot Number cascade. Lot Number QB Lot Status table Filtered to lots where Community = [selected Community] ; shows only lots with Asset Status ≠ Occupied. This prevents creating rehab records for occupied lots. Asset Status Lookup from Lot Auto-populated after Lot Number is selected; read-only on the Rehab Record form. Unit Make / Model / Year Lookup from Lot / Asset Auto-populated if available in the QB Asset Status table; can be overridden by inspector. 8.2 Secondary Cascade: Task Trade → Vendor Field Source Cascade Logic Trade Category Rehab Tasks form User selects trade (Plumbing, Electrical, HVAC, Roofing, etc.). Drives the Vendor ID dropdown. Vendor ID SharePoint Vendor Master (via Pipelines) Filtered to vendors where Trade Category = [selected Trade] AND States Served includes [Community State] AND Active = Yes . Preferred vendors appear first. Vendor Name Lookup from Vendor ID Auto-populated from SharePoint Vendor Master after Vendor ID is set; read-only. 8.3 Tertiary Cascade: Rehab Stage → Allowed Status Field Context Cascade Logic Rehab Status Rehab Records Available status values are constrained by the current Stage. Moving backward (e.g., Walkthrough → Triggered) is disallowed via form validation rule (Gate Rule G-RH-01). Task Status Rehab Tasks Available transitions are constrained by parent Rehab Status: Task completion is blocked if Rehab Status = Triggered or Walkthrough (tasks cannot close before work phase begins). 8.4 Implementation Note QB Cascading Dropdown Mechanism: QuickBase cascading dropdowns are implemented using a lookup field paired with a formula-based filter on the child field. The parent field value is passed as a filter parameter to the child field's record picker. For the Vendor cascade, the filter is applied via QB Pipelines since the source (SharePoint) is external to QB. The exact Pipelines implementation is tracked in O-WF002-NEW-05 (§11). 9. Rules are evaluated in order; the first failing rule blocks the transition.
