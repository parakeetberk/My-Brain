Section 01 Document Purpose WF002 — Rehab

This specification defines the complete Quickbase (QB) tables, workflow stages, automations, gate rules, and FastField form required to build Workflow #002: Rehab. WF002 manages the end-to-end process of taking an existing home from a Rehab disposition decision — made via the TBD Report or manually — through completed rehabilitation, final walkthrough approval, and handoff notification to the listing team.

WF002 is independent of WF001 (Home Ordering). WF001 covers new homes ordered from manufacturers. WF002 covers existing homes in the portfolio that require rehabilitation before they can be re-listed or re-occupied.

System of Record: Rent Manager (RM) remains the authoritative source for asset data, financial records, insurance, and lease history. This build complements RM — it does not replace or auto-modify any RM records. All RM field references in QB are cross-references only. No data is written back to Rent Manager from QB.
BoundaryDetail
In ScopeAll 9 rehab workflow stages; QB tables (Lot Status ref, Asset Status ref, Rehab Records, Rehab Tasks, Walkthrough Records, Vendors); FastField Rehab Walkthrough Punchlist form with photo capture; FastField → QB webhook integration; all automations and gate rules defined in this document; 68-community Communities table (from dw_PDS.xlsx)
Out of ScopeRent Manager record creation or modification; marketing execution after listing; Workflow #001 (new home ordering); invoice processing or payment; vendor portal access; WF003 Asset Disposition Review meeting design (separate workflow — see Q-037)
Dependent WorkflowsWF003 Asset Disposition Review (proposed) — weekly Monday meeting assigns Rehab / Demo / Turn for Sale dispositions; triggers WF002 when disposition = Rehab. Move Out workflow — completed move-out can trigger WF002. Listing workflow — WF002 notifies listing team at Stage 8; listing team initiates listing manually.

Asset Disposition Review Meeting Weekly Monday meeting run by Asset Management. Participants: Asset Management, Ops, Construction, and Sales. When disposition = Rehab is recorded in QB, automation A-RH-01 creates a new Rehab Record automatically. Note: Meeting currently runs outside QB. WF003 (Asset Disposition Review) proposed to bring it into QB — see Open Item O-WF002-NEW-01 and Q-037. Asset Management team (meeting recorder)

Move Out Completed Move Out record can trigger WF002 when the disposition assigned at move-out = Rehab. Automated on Move Out completion

Listing Handoff (Important)

Listing handoff = notification only. When a home is Approved as Ready to Market (Stage 8), Automation A-RH-07 sends a notification to the listing team: "Home at [Community] Lot [Lot] has been approved. Please complete a Listing Request Form." The notification includes a link to the Listing Request form. The listing team initiates listing manually — WF002 does not auto-create a listing record.

The Rehab Walkthrough form is built in FastField and completed by the inspector in the field at each unit. The form captures 37 condition checklist items (each with an optional photo), calculated results, and a final status determination with inspector signature. All data syncs back to QuickBase upon form submission.

6. Vendor Architecture

Vendors engaged during a rehab are stored in a SharePoint list (not as native QuickBase records) and referenced via a lookup or manual entry in QB. This approach leverages the existing SharePoint vendor management infrastructure and avoids duplicating master vendor data in QuickBase.

6.1 Storage Architecture

Design Decision — SharePoint as Vendor Master: Vendor records live in a SharePoint list (Parakeet Communities → Operations → Vendor Master). QuickBase stores only the vendor's short name / ID and the associated bid amount on each Rehab Task. Full vendor detail (contact, license, insurance) is maintained in SharePoint.
OptionLocationTrade-offs
Option A — SharePoint Lookup (Selected)SharePoint ListSingle source of truth for vendor master; no QB licensing overhead for vendor contacts; existing compliance tracking remains intact
Option B — QB Native Vendor TableQuickBaseTighter pipeline; requires duplicate entry; license cost for additional QB records if >10k rows
Option C — Manual Free-Text in TasksQB Rehab TasksLowest friction for launch; loses reporting and de-duplication; not recommended for production

8. Cascading Dropdowns

WF002 uses cascading dropdown logic in QuickBase to reduce data entry errors and narrow selection lists to contextually valid choices. The primary cascade chain is Community → Lot Number → (pre-populated unit data). A secondary chain filters the Vendor ID dropdown by trade category and by the community's state.

8.1 Primary Cascade: Community → Lot

FieldSourceCascade Logic
CommunityQB Communities tableUnrestricted dropdown of all Active communities (Short Name + Display Name). Drives the Lot Number cascade.
Lot NumberQB Lot Status tableFiltered to lots where Community = [selected Community]; shows only lots with Asset Status ≠ Occupied. This prevents creating rehab records for occupied lots.
Asset StatusLookup from LotAuto-populated after Lot Number is selected; read-only on the Rehab Record form.
Unit Make / Model / YearLookup from Lot / AssetAuto-populated if available in the QB Asset Status table; can be overridden by inspector.

8.2 Secondary Cascade: Task Trade → Vendor

FieldSourceCascade Logic
Trade CategoryRehab Tasks formUser selects trade (Plumbing, Electrical, HVAC, Roofing, etc.). Drives the Vendor ID dropdown.
Vendor IDSharePoint Vendor Master (via Pipelines)Filtered to vendors where Trade Category = [selected Trade] AND States Served includes [Community State] AND Active = Yes. Preferred vendors appear first.
Vendor NameLookup from Vendor IDAuto-populated from SharePoint Vendor Master after Vendor ID is set; read-only.

8.3 Tertiary Cascade: Rehab Stage → Allowed Status

FieldContextCascade Logic
Rehab StatusRehab RecordsAvailable status values are constrained by the current Stage. Moving backward (e.g., Walkthrough → Triggered) is disallowed via form validation rule (Gate Rule G-RH-01).
Task StatusRehab TasksAvailable transitions are constrained by parent Rehab Status: Task completion is blocked if Rehab Status = Triggered or Walkthrough (tasks cannot close before work phase begins).

8.4 Implementation Note

QB Cascading Dropdown Mechanism: QuickBase cascading dropdowns are implemented using a lookup field paired with a formula-based filter on the child field. The parent field value is passed as a filter parameter to the child field's record picker. For the Vendor cascade, the filter is applied via QB Pipelines since the source (SharePoint) is external to QB. The exact Pipelines implementation is tracked in O-WF002-NEW-05 (§11).

9. Automations

WF002 includes twelve QuickBase Pipelines automations (A-RH-01 through A-RH-12). Each automation is a discrete, named pipeline. Automations are shown below in trigger-sequence order; several are co-dependent (e.g., A-RH-01 must fire before A-RH-02 is relevant).

ID Name Trigger Action & Notes
A-RH-01 Rehab Record Creation Manual (PM), TBD Report, or Move-Out event Creates a new Rehab Record with Rehab Status = Triggered. Sets Triggered Date to today. Validates that Community and Lot Number are provided before creation. See §2.1 for trigger details.
A-RH-02 FastField Form Dispatch Rehab Status changes to Triggered Pushes a pre-populated FastField form link to the assigned inspector via email/push notification. Form pre-fills Community, Lot Number, and Rehab Record ID from the QB record.
A-RH-03 Walkthrough Status Sync FastField form submitted Receives FastField webhook payload; updates QB Walkthrough Record fields (Inspector, Date, Status, Photo URLs, Fail count). Sets Rehab Status = Walkthrough Complete if Overall Walkthrough Status = Pass or Fail — Ready.
A-RH-04 Bid Package Notification Rehab Status changes to Walkthrough Complete Sends email to PM and Rehab Coordinator notifying that the walkthrough is complete and the unit is ready for bid solicitation. Includes link to QB Rehab Record and summary of fail count.
A-RH-05 Rehab Task Auto-Creation FastField form submitted (Fail items) For each checklist item marked Fail in the FastField submission, creates one Rehab Task record linked to the parent Rehab Record. Sets Task Name from item name, Task Status = Open, Trade Category from item section mapping.
A-RH-06 Bid Approval Workflow Rehab Status changes to Bid Submitted Routes bid for approval based on Total Bid Amount: ≤$2,500 → PM approval only; $2,501–$10,000 → Regional Manager; >$10,000 → VP Operations. Creates an approval task in QB assigned to the appropriate approver.
A-RH-07 Work Order Issuance Rehab Status changes to Bid Approved Generates and emails a formatted work order (QB report export) to each vendor with at least one approved Rehab Task. Sets Work Start Date = today + 3 business days (default; PM can override). Sets Rehab Status = In Progress.
A-RH-08 Task Completion Monitor Rehab Task Task Status changes to Complete Checks if all Rehab Tasks linked to the parent Rehab Record are Complete. If yes, sets Rehab Status = Punch List and notifies PM to schedule a final walkthrough.
A-RH-09 Punch List Re-Inspect Dispatch Rehab Status changes to Punch List Re-dispatches FastField form (same template) for the punch list inspection. Pre-fills previous fail items as context. Inspector re-assesses only previously failed items plus any new concerns.
A-RH-10 Rehab Completion & Financial Close Rehab Status changes to Complete Sets Rehab Complete Date. Calculates Total Actual Cost from sum of all Rehab Task Actual Cost fields. Calculates Variance $ and Variance %. Updates Lot Status Asset Status = Available.
A-RH-11 Listing Handoff Notification Rehab Status changes to Complete Sends notification email to the Leasing team (recipient list configurable per community) with unit details, rehab summary, and total cost. Does not auto-create a listing record; notification only. See §2.2.
A-RH-12 SLA / Age Alert Scheduled daily at 6:00 AM ET Runs daily; flags any Rehab Record where Days Since Triggered exceeds SLA threshold by stage: Triggered >3 days without Walkthrough → Alert; Walkthrough Complete >5 days without Bid → Alert; In Progress >30 days without Completion → Escalation. Sends alert email to PM and Regional Manager.

10. Gate Rules

Gate rules are enforced in QuickBase via form validation logic and Pipelines guards. They prevent invalid state transitions and ensure data integrity across the rehab lifecycle. Rules are evaluated in order; the first failing rule blocks the transition.

ID Gate Name Transition Blocked Condition & Error Message
G-RH-01 No Backward Status Any → earlier Stage Condition: New Rehab Status has a lower stage sequence number than the current status.
Error: "Status cannot move backward. Contact your administrator to revert if needed."
G-RH-02 Walkthrough Required Before Bid Triggered → Bid Submitted Condition: Walkthrough Status is blank or Pending.
Error: "A completed walkthrough is required before submitting a bid."
G-RH-03 Bid Amount Required Walkthrough Complete → Bid Submitted Condition: Total Bid Amount is blank or $0.
Error: "Total Bid Amount must be entered before submitting for approval."
G-RH-04 Approval Required Before Work Bid Submitted → In Progress Condition: Bid Approval Status ≠ Approved.
Error: "Bid must be approved before work can begin. Current approval status: [Bid Approval Status]."
G-RH-05 All Tasks Must Close In Progress → Punch List Condition: COUNT of Rehab Tasks where Task Status ≠ Complete or Cancelled > 0.
Error: "[N] task(s) are still open. All tasks must be closed before moving to Punch List."
G-RH-06 Punch List Pass Required Punch List → Complete Condition: Punch List Status ≠ Passed.
Error: "Punch list inspection must be completed and passed before marking the rehab Complete."
G-RH-07 Actual Costs Required at Close Punch List → Complete Condition: Any Rehab Task with Task Status = Complete has blank Actual Cost.
Error: "Actual cost must be entered for all completed tasks before closing the rehab."
G-RH-08 Occupied Lot Block Record Creation Condition: Selected Lot's Asset Status = Occupied at time of Rehab Record creation.
Error: "This lot is currently occupied. A rehab record cannot be created for an occupied lot."
