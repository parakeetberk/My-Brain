This gameplan organizes all 91 Parakeet Communities SOPs into a sequenced, interconnection-aware build roadmap for the QB + FastField operational OS. It extends the approach established in WF001–WF003 (Home Ordering, Rehab, Disposition Review) across the full operational surface area — from resident move-in to eviction, from acquisitions to accounting, from field inspections to legal compliance.

The document answers three questions that an ad hoc sprint approach would not:

  • What shared data tables must exist before any dependent workflow is built — so you never have to rebuild a workflow because its data model wasn’t ready (the most expensive mistake in QB builds).
  • Which workflows must precede others — because workflow B pulls records created by workflow A, or workflow B’s automation fires based on a status set by workflow A.
  • What requires a FastField form vs. what lives entirely in QB — so field staff have exactly the tools they need, and the back-office team has everything automated behind the scenes.
✓ What’s Already Done (Wave 0)

5 workflows are already specced and represent the first deployable layer of the OS: WF001 Home Ordering (LOCKED v1.2), WF002 Rehab (LOCKED v1.3), WF003 Disposition Review (LOCKED v1.1), WF004 Move Out (DRAFT v1.0), and WF006 Listings (DRAFT v1.0). These represent approximately $3M–$5M in annual asset movement handled by the system.

⚠ Critical Pre-Work Before Any New Build

Before Waves 1–8 can begin, five shared QB reference tables must be built first. Without them, every downstream workflow will be designed around missing data and will require retroactive rebuilding. This pre-work is estimated to take 1–2 weeks but prevents 3–6 weeks of rework later. See Section 4.

ⓘ How to Use This Document

Work through the waves in order. Each wave section identifies: which SOP(s) it covers, what WF number it is assigned, whether it needs a FastField form, what QB tables it reads from and writes to, what automations it fires, and what decisions are needed before speccing can begin. The full SOP-to-WF mapping table in Section 6 is the master reference for all 91 SOPs.

2. Foundation Principles — Why Order Matters
Principle 1: Shared Tables First, Workflows Second

Every QB workflow either creates records in shared tables or reads records from them. If you build WF019 (Eviction Pipeline) before WF005 (Move In) creates Resident records, the eviction workflow has nothing to look up. You cannot auto-populate “resident name,” “lease start date,” or “community” — the very fields that make automation possible instead of just digital paperwork.

The rule: shared tables and the workflows that populate them must be built before any workflow that reads from them. This is why the Residents table, Lease Records table, and Work Orders table are pre-work, not Wave 1 tasks.

Principle 2: Revenue Protection Before Operations Optimization

Collections, Stipulations, and the Eviction Pipeline are Wave 2 — right after the resident lifecycle workflows that create the data. A single 30-day delay in an eviction pipeline due to missing documentation or missed cure period deadlines can cost $1,500–$3,000 in lost rent plus legal fees. The system needs to protect revenue before it optimizes field operations.

Principle 3: State-Specific Rules Are Not Edge Cases

Parakeet operates in 8 states (AL, FL, GA, MA, MI, NC, SC, WV). FL Chapter 723 lot rent increase rules, MA’s 30-day eviction notice requirement, and GA’s 60-day rent increase notice are hard deadlines — not preferences. Any workflow that touches rent increases, evictions, or lease renewals must encode state-specific logic as QB conditional rules or automation triggers. This is not optional and must be designed in from the start.

Principle 4: FastField = Field Capture, QB = Workflow Engine, RM = System of Record

This three-system architecture was established in WF001 and governs every subsequent workflow:

  • FastField: Any form completed by a CM or field staff person on-site or on a mobile device. Condition inspections, move-in/move-out reports, site visit checklists, utility verification. FastField handles the data collection; QB handles the resulting workflow steps.
  • QB: Workflow stages, gate rules, automations, approval routing, record creation, and reporting. QB never replaces RM — it operates in the gaps between RM capabilities and field reality.
  • RM (Rent Manager): Financial ledger, charge schedules, lease records, security deposits. QB may display RM data for context but never writes financial records to RM directly — all RM updates flow through the daily batch CSV sync at 6 PM ET.
Principle 5: No Rebuild Debt

Rebuild debt is what happens when a workflow is designed in isolation and later needs to be rewired because a dependency wasn’t anticipated. Examples of rebuild debt to avoid:

  • Building Eviction (WF019) before Residents table → must rebuild the lookup relationships later
  • Building Collections (WF017) without Lease Records → can’t auto-pull balance due or cure period deadline
  • Building Utility Activation (WF027) without community-level Utility Accounts table → can’t auto-assign utility provider
  • Building Rent Increase (WF021) without state field in community record → can’t apply state-specific notice requirements

The wave sequencing in this document is designed specifically to prevent these scenarios.

4. Shared Reference Tables — Pre-Work (Must Build Before Wave 1)

These five QB tables are read by three or more workflows each. Building them once, correctly, before any downstream workflow is specced prevents the most common and expensive form of rebuild debt. These are not workflow tables — they are the data foundation the entire OS sits on.

👥 Residents Table
CRITICAL — Build First
Master registry of all current and former residents across all 68 communities. One record per resident. This is the single most important missing table in the current QB build.
Core Fields: Resident ID (RES-YYYY-###), Full Name, Community (lookup), Lot # (lookup), RM Resident ID, Phone, Email, Status (Active / Former / Evicted / Deceased), Move-In Date, Expected Move-Out Date, Resident Type (POH Owner / Rental / LTP / RTO / Promissory Note)

Feeds Into: WF005 Move In, WF004 Move Out, WF016 Lease Renewal, WF017 Collections, WF018 Stipulation, WF019 Eviction, WF020 Post-Eviction Title, WF021 Rent Increase, WF028 Rental Inspections, WF013 Incident Report, WF029 Violations — 21 workflows total

RM Sync: Resident records originate in RM; QB Residents table imports via daily batch CSV. QB writes back status changes via automation (not manually).
📃 Lease Records Table
CRITICAL — Build With Residents
One record per active or historical lease. Tracks lease type, term, rent amount, renewal status, and expiration date. Required for Collections, Eviction, and Lease Renewal to auto-populate key dates and amounts.
Core Fields: Lease ID (LS-YYYY-###), Resident (lookup → Residents), Community (lookup), Lot #, Lease Type (Standard / LTP / Rental / RTO), Monthly Rent, Lease Start, Lease End, State (FL/GA/SC/MA/NC/AL/MI/WV), Status (Active / Expired / Month-to-Month / Evicted / Renewed), RM Charge Schedule ID

Feeds Into: WF004 Move Out (lease end date), WF005 Move In (creates record), WF016 Lease Renewal (trigger + notice period calc), WF017 Collections (balance due + state cure period), WF018 Stipulation (payment plan terms), WF019 Eviction (lease type determines POH vs rental path), WF021 Rent Increase (state-specific notice period) — 12 workflows total

State Logic Required: Cure period by state (FL: 5 bd, SC: 5 days, GA: 3 bd, NC: 10 days, MA: 30 days) must be stored or derivable from the State field on the Lease record.
🔨 Work Orders Table
HIGH PRIORITY
Master log of all maintenance, repair, and infrastructure work orders across all communities. Shared by Site Visit Follow-Up, Rental Inspections, and Month-End reporting.
Core Fields: Work Order ID (WO-YYYY-###), Community (lookup), Lot # (optional lookup), Category (Electrical / Plumbing / HVAC / Grounds / Infrastructure / General), Description, Priority (Emergency / Urgent / Standard), Status (Open / In Progress / Complete / Deferred), Assigned To (vendor or staff), Date Opened, Date Completed, Cost

Feeds Into: WF008 Site Visit Inspection (generates WOs), WF009 Weekly Maintenance, WF010 Monthly Equipment, WF028 Rental Inspections (generates WOs on fails), WF011 Month End (open WO count), WF029 Violations (WO may accompany notice) — 6 workflows total
🏠 Title & Document Records Table
HIGH PRIORITY
Tracks the chain of title for all community-owned homes (POH) and homes in process. Required before any title transfer workflow can be built. Prevents duplicate records and conflicting title actions on the same asset.
Core Fields: Title Record ID (TTL-YYYY-###), Asset / Home (lookup → Lots), Current Owner (Parakeet / Resident / Lender / Estate), Title Status (Clear / Pending Transfer / Liened / Deceased Owner / In Process), HUD Label #, Serial Number, Year, Make/Model, State, County, Legal Description, Current Lender (if liened), Attorney File # (Vector Law / FL Fast Title)

Feeds Into: WF020 Post-Eviction Title, WF022 Home Closing, WF023 POH Sales Title Transfer, WF024 Asset Title Transfer, WF005 Move In (closing docs), WF039 Acquisitions Transition — 8 workflows total
⚡ Utility Accounts Table
HIGH PRIORITY
Registry of all utility accounts at the community level (electric, water/sewer, gas, trash) and lot level where individual metering applies. Required before any utility activation or transfer workflow can be built.
Core Fields: Utility Account ID (UTL-YYYY-###), Community (lookup), Lot # (optional), Utility Type (Electric / Water / Sewer / Gas / Trash / Submetered), Provider Name, Account Number, Account Holder (Parakeet / Resident), Status (Active / Inactive / Pending), Billing Type (Master-metered / Individual / RUBS / Sub-metered), Setup Date

Feeds Into: WF005 Move In (utility transfer to resident), WF004 Move Out (utility transfer back to Parakeet), WF027 Utility Activation New Home, WF027 Utility Activation Rehab, WF035 Utility Recapture Reporting, WF040 Utility Onboarding Acquisitions — 7 workflows total
5. Build Wave Plan — Waves 0 Through 8
Wave Sequencing Logic

Waves are ordered by data dependency first, business criticality second. A workflow in Wave 3 cannot be specced until all Wave 1 and Wave 2 workflows are at least in draft, because Wave 3 workflows reference records created by Wave 1–2. Within each wave, workflows can be specced in parallel. Waves are not calendar weeks — they are logical dependency layers. Expect 2–4 weeks per wave depending on complexity and available input from Operations, Legal, and Accounting.
